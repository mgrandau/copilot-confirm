# Journal - December 4, 2025

## Origin Story

This is a retroactive journal entry. The project was built before the [Human-AI Intent Transfer Principles](https://mgrandau.medium.com/human-ai-intent-transfer-principles-b6e7404e3d26?source=friends_link&sk=858917bd3f4a686974ed6b6c9c059ac8) were defined — it was the first attempt at improving the human-AI coding workflow, and the experience building it contributed to those principles being written.

## The Problem

GitHub Copilot's default behavior is to act immediately. You describe a problem, it starts solving it. Most of the time that's fine. But when the problem is ambiguous — refactoring, architecture decisions, anything with multiple valid approaches — Copilot picks one and runs with it. If it picks wrong, you've lost time undoing work you never asked for. Worse, you might not even notice it picked wrong until you're reviewing the output.

The core frustration: **Copilot was deciding before I had decided.** It was optimizing for speed when the bottleneck was actually clarity of intent.

## The Idea

What if Copilot paused and showed you what it was thinking before it acted? Not a long analysis — just 2-3 options with rough confidence percentages. You pick one, it executes. Simple.

The percentages aren't precise — they're the AI's rough estimate of which approach best fits the context. But they serve a purpose: they make the AI's reasoning visible. If you see "DI pattern (70%)" and think "no, this is simpler than that" — the percentages told you something useful even when they're wrong.

## What We Built

A pip-installable package that copies two files into your project:

1. **Agent file** (`copilot_confirm.agent.md`) — defines the persona: "you are an agent that confirms before acting"
2. **Instruction file** (`confirmation_workflow.instructions.md`) — defines the protocol: preview options → wait → execute → suggest next steps

The installer is structurally identical to what became copilot-journal — Protocol-based DI, frozen dataclasses, cross-platform path resolution. This project established the pattern that the other installers followed.

## Key Design Decisions

### Two files, not one

The agent file and instruction file serve different purposes. The agent file defines *who* Copilot is in this mode ("an enhanced agent with intelligent confirmation workflow"). The instruction file defines *how* it behaves (the numbered options → waiting → execute protocol). Separating them means you could swap the workflow without changing the persona, or apply the persona to a different workflow.

**Why not one file?** A single combined file would work, but VS Code treats agents and instructions differently — agents appear in the agent dropdown, instructions apply passively. Combining them would either lose the dropdown entry or force the workflow to be always-on with no way to toggle it.

### Minimal instructions

The confirmation workflow started longer — more examples, more edge cases, more "never do X" rules. Through usage, it became clear that LLMs follow short, structured instructions more reliably than long prose. The current version is ~15 lines.

**What got cut:** Detailed examples of multi-step workflows, guidance on handling ambiguous user responses, instructions for when to skip confirmation on trivial tasks. All removed because they added tokens without improving compliance. The LLM either follows "🛑 WAITING" or it doesn't — more words about *how* to wait don't help.

### Confidence percentages

The percentages aren't calibrated — Copilot isn't actually computing probability distributions. They're the LLM's rough estimate of fit, presented as numbers to force it to rank options rather than hedging with "both could work."

**Why not just a list without percentages?** Without numbers, Copilot tends to present options as equally valid ("you could do A or B"). The percentages force a commitment: one option is the lead, the others are alternatives. That structure helps the developer decide faster — you're not comparing equals, you're reviewing a recommendation.

### The installer pattern

This was the first project where we used Protocol-based dependency injection for a file-copying installer. The pattern worked well enough that it was reused in copilot-journal with minimal changes. Both projects share the same architecture: `FileSystemProtocol` / `EnvironmentProtocol` for testing, `PathResolver` for cross-platform paths, `AgentInstaller` as the core logic.

**Why not just copy files with a shell script?** Two reasons: (1) cross-platform support — Windows, macOS, and Linux all have different VS Code config paths, and (2) testability — the Protocol DI pattern means we have 36 tests at 100% coverage without touching the filesystem.

## What This Project Taught Us

1. **LLMs follow short instructions better than long ones.** The first draft of the confirmation workflow was 3x longer and less effective.
2. **The pause is the feature, not the options.** Users don't always care about the specific options — they care that Copilot stopped and asked instead of plowing ahead.
3. **The installer pattern is reusable.** Protocol-based DI for file copying is overkill for one project but pays off when you have three projects sharing the structure.
4. **AI behavior customization is just file installation.** The hard part isn't the installer — it's the 15 lines of instructions that actually change how Copilot behaves.

## Connection to Later Work

This project directly led to:
- **copilot-journal** — same installer pattern, different agent files (journaling instead of confirmation)
- **ai-session-tracker-mcp** — the idea that AI workflows should be measured, not just modified
- **Human-AI Intent Transfer Principles** — the experience of building a "pause and confirm" workflow crystallized into Principle 1 (Human Intent Leads) and Principle 8 (Calibrate Trust by Consequence)
